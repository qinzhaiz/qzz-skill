# 常见错误

## 错误 1：从不测试备份恢复

**症状**：备份脚本跑了半年，磁盘出问题后发现备份文件是坏的（磁盘已经坏了几个月了，备份的都是空文件）。

**原因**：备份脚本可能因为磁盘空间不足悄悄失败了，或者文件系统损坏导致备份文件不完整。没有人验证过 → 备份等于没做。

**怎么修**：每月至少做一次恢复演练，验证备份文件可用。恢复后至少检查：(1) 数据库能正常启动，(2) 关键表的数据行数在合理范围内，(3) 最近的数据能查到。

## 错误 2：binlog 保留时间太短

**症状**：全量备份是 7 天前的，但 binlog 也只保留了 7 天。误删发生在全量备份后第 8 天——binlog 已经被自动清理了。只能恢复到 7 天前的数据。

**原因**：`expire_logs_days = 7` 意味着 7 天后 binlog 自动删除。如果全量备份周期也是 7 天，备份之间的 binlog 被删了 → 时间点恢复只能恢复到上次全量备份时刻。

**怎么修**：binlog 保留时间至少是全量备份周期的 2 倍。比如全量每周一次 → binlog 保留 14 天。同时确保 binlog 文件有足够的磁盘空间。

## 错误 3：直接在主库上做恢复操作

**症状**：为了恢复一张误删的表，在主库上回放大量 binlog——导致主库 CPU 和 IO 飙高，线上业务受影响。

**原因**：恢复操作（特别是全量导入 + binlog 回放）是资源密集型操作，不应该和线上业务争资源。

**怎么修**：恢复操作在独立服务器上做。恢复完成后只把需要的数据导入生产库（如只恢复被误删的那张表）。这就是为什么需要在从库做备份，恢复时也可以利用从库的硬件。
