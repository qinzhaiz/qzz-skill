# 读写分离

> 主库负责写，从库负责读——把读写流量分开，用水平扩展提升整体吞吐量。

## 为什么需要它

单台 MySQL 的能力有上限。当读请求越来越多，单机 CPU 和 IO 都会饱和。大部分应用的读写比例是 80% 读 + 20% 写——读是瓶颈。读写分离的思路：主库只处理写请求，把读请求分散到多台从库——每加一台从库，读能力就线性扩展。

## 它是什么

读写分离是基于主从复制的一种架构模式：

```
应用层 → 中间件(路由) ─→ 主库（INSERT/UPDATE/DELETE）
                        ─→ 从库1（SELECT）
                        ─→ 从库2（SELECT）
                        ─→ 从库3（SELECT）
```

**中间件**负责：识别 SQL 是读还是写 → 路由到正确的库 → 负载均衡从库之间的读请求。

### 常见中间件

| 方案 | 特点 | 适用场景 |
|------|------|---------|
| **MySQL Router** | MySQL 官方出品，简单轻量 | 简单读写分离 |
| **ProxySQL** | 功能强大，SQL 级别的路由和缓存 | 复杂场景（需要规则路由） |
| **应用层路由** | 代码里手动选择数据源（如 Spring AbstractRoutingDataSource） | 小项目，不想加额外组件 |

## 怎么工作

### 基本路由规则

```
SELECT → 从库（任意一个，负载均衡）
INSERT/UPDATE/DELETE → 主库
SET @var = value → 主库（事务外的 SET 语句也应该走主库）
事务中的语句 → 全走主库（事务内涉及写操作）
```

### 关键问题：复制延迟导致的"写完读不到"

```
用户 POST 提交 → 主库写入 → 返回成功 → 跳转到列表页
                                      ↓
                          SELECT 到从库 → 数据还没同步过来？
                                      ↓
                          用户看不到刚提交的数据！
```

解决方案：

1. **强制读主库**：写操作后的关键读操作走主库。如"下单后跳转订单详情"——这个详情页读主库。
2. **延迟阈值**：从库延迟超过 N 秒时，不再向它路由读请求，等它追上。
3. **应用层标记**：写入后在缓存中标记"这行数据刚更新过"，读请求先查缓存（命中直接返回，不查从库）。

## 怎么用

```sql
-- 从库配置只读
SET GLOBAL read_only = ON;
SET GLOBAL super_read_only = ON;  -- MySQL 5.7.8+

-- 监控从库延迟（应用层判断该从库是否可用）
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: 0 → 正常
-- Seconds_Behind_Master: 30 → 延迟 30 秒，暂时不要路由读请求给它
```

### ProxySQL 基础配置思路

```sql
-- ProxySQL 配置示例（在 ProxySQL 管理端执行）
-- 1. 定义后端服务器
INSERT INTO mysql_servers VALUES
(1, '192.168.1.1', 3306),  -- 主库
(2, '192.168.1.2', 3306),  -- 从库1
(3, '192.168.1.3', 3306);  -- 从库2

-- 2. 定义读写分组
INSERT INTO mysql_replication_hostgroups VALUES
(10, 20);  -- 写组 10（主库），读组 20（从库）

-- 3. 设置路由规则
INSERT INTO mysql_query_rules (rule_id, match_digest, destination_hostgroup)
VALUES (1, '^SELECT.*FOR UPDATE$', 10),     -- SELECT FOR UPDATE 走主库
       (2, '^SELECT.*$', 20),                -- 普通 SELECT 走从库
       (3, '^INSERT|^UPDATE|^DELETE', 10);  -- 写操作走主库
```

## 注意事项

1. **读写分离增加了系统复杂度**——多了一个中间件需要维护和监控。小项目先考虑升级硬件，确实需要再上读写分离。
2. **复制延迟是无法消除的**——只要用异步复制，从库永远比主库慢一点点。设计业务逻辑时要考虑这个前提。
3. **不要无限加从库**——每个从库都在拉 binlog，过多从库会增加主库的网络和 IO 压力。通常 3-5 台足够大多数场景。
