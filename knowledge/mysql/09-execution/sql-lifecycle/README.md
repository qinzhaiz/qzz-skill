# SQL 执行流程

> 一条 SQL 从客户端输入到返回结果，在 MySQL 内部经历了什么过程。

## 为什么需要它

写过 SQL 的人都知道输入 `SELECT * FROM user WHERE id = 1` 能拿到结果。但这个过程中 MySQL 到底做了什么？理解这个流程，才能理解为什么同样的 SQL 有时候快有时候慢，为什么建立了索引优化器却不用。

## 它是什么

MySQL 分为两层：**Server 层**和**存储引擎层**。一条 SQL 的执行经历了 Server 层的四个组件：

```
客户端 → 连接器 → 分析器 → 优化器 → 执行器 → 存储引擎 → 返回结果
```

| 组件 | 干了什么 | 类比 |
|------|---------|------|
| **连接器** | 建立连接、验证身份、读取权限 | 公司前台——确认你是谁 |
| **分析器** | 词法分析 + 语法分析，构建语法树 | 语法老师——拆句子结构 |
| **优化器** | 选索引、定 JOIN 顺序、生成执行计划 | 导航软件——选最优路线 |
| **执行器** | 检查权限，调存储引擎接口取数据 | 工人——按计划干活 |

MySQL 8.0 已经删除了查询缓存——它只在表很少更新的场景有用，大多数时候反而是累赘。

## 怎么工作

以 `SELECT * FROM T WHERE ID = 10` 为例：

1. **连接器**：TCP 握手 → 身份认证 → 从权限表读取你的权限（之后修改权限不影响已建立的连接）
2. **分析器**：词法分析（识别 SELECT 是查询、T 是表名、ID 是列名）→ 语法分析（检查语法是否正确）→ 输出语法树
3. **优化器**：判断 ID 上有索引 → 决定用索引而不是全表扫描 → 生成执行计划
4. **执行器**：检查你对 T 表有没有 SELECT 权限 → 调 InnoDB 的 `ha_index_read()` 接口 → 取到 ID=10 这行 → 返回

## 怎么用

不需要手动做什么，但可以通过这些工具观察每一步的输出：

```sql
-- 看优化器选择了什么执行计划
EXPLAIN SELECT * FROM user WHERE id = 1;

-- 看优化器实际重写的 SQL 和更详细的代价评估
EXPLAIN FORMAT=JSON SELECT * FROM user WHERE id = 1;

-- 看优化器选择索引时的决策过程
SET optimizer_trace = 'enabled=on';
SELECT * FROM user WHERE id = 1;
SELECT * FROM information_schema.optimizer_trace\G
```

## 注意事项

1. **权限在连接建立时读取**——连接后再改权限不影响已建立的连接。新权限下次连接才生效。
2. **优化器可能选错索引**——它基于统计信息（`innodb_stats_persistent`）做判断，如果统计信息不准可能选全表扫描而不是用索引。
3. **连接有超时**——`wait_timeout` 默认 8 小时，空闲超时的连接会被断开。
