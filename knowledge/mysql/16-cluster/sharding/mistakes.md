# 常见错误

## 错误 1：过早分库分表

**症状**：数据量才几十万行就开始分库分表。引入了分布式事务、跨分片查询、数据迁移等复杂性——开发和运维成本翻了好几倍。

**原因**：被"大厂架构"影响了判断。大厂是因为单表几亿行、QPS 几十万才不得不分。绝大多数项目一辈子也到不了这个量级。

**怎么修**：先优化索引和 SQL → 加缓存 → 升级硬件 → 读写分离 → 垂直拆分（按业务拆库）→ 直到单表真正成为瓶颈才考虑水平分片。单表 < 500 万行，索引合理的情况下完全不用分。

## 错误 2：分片键选错导致热点

**症状**：分片后大部分请求集中在一个分片上，其他分片基本空闲。

**原因**：分片键选了一个分布不均匀的字段。比如按"状态"分片（大部分数据是"进行中"），或者按"时间"分片（今天的数据全在一个分片）。

**怎么修**：选基数大、分布均匀的字段。通常用 user_id、order_id 这种自增或随机 ID。也可以自定义分片算法（如一致性哈希）。

## 错误 3：扩容时数据迁移没规划

**症状**：4 个分片不够了，需要扩到 8 个。发现现有数据的 user_id % 4 对不上 user_id % 8，所有数据都需要重新分布。

**原因**：用取模算法做分片，扩缩容需要数据迁移。4 → 8 意味着 3/4 的数据要搬家。

**怎么修**：规划时就考虑扩容。用一致性哈希算法（扩缩容只影响相邻节点），或者预留足够分片数（比如一开始就 32 个分片但只部署在 4 台机器上，扩容时移动分片而不是拆分数据）。
