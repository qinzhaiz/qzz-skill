# 常见错误

## 错误 1：信任"前端已经校验了"

**症状**：后端代码直接用前端传来的参数拼接 SQL，"前端已经做了格式校验，不会有问题"。

**原因**：前端校验只影响用户体验，不能当作安全防护。攻击者直接用 curl/Postman 发请求，绕过了所有前端校验。

**怎么修**：后端永远不信任用户输入。服务端做参数化查询（防御注入）+ 白名单验证（防御非法值）。

## 错误 2：对输入做转义而不是用参数化查询

**症状**：自己写转义函数处理单引号——`user_input.replace("'", "\\'")`。看起来很安全，但总有遗漏的边界情况。

**原因**：手动转义是"黑名单"思路——你不知道攻击者会用什么新花样。参数化查询是"白名单"思路——所有数据都安全，从根本上杜绝注入。

**怎么修**：用参数化查询代替手动转义。转义容易出错（不同字符集、编码方式），参数化查询由数据库引擎保证安全。

## 错误 3：ORM 的原生 SQL 也拼接

**症状**：用了 ORM 但还是出现注入漏洞。代码审查发现有人用 `orm.raw()` 方法拼接了用户输入。

**原因**：ORM 的安全保证仅限于它的查询构建器。`db.raw()`、`db.execute()` 仍然可以拼接字符串——这些方法的用户输入不会自动参数化。

**怎么修**：如果是 ORM 的查询构建器（`Model.where()`），放心用。如果是原生 SQL（`raw()`, `execute()`），必须手动传参数（不要拼接）。
