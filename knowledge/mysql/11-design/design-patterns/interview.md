# 面试题

## Q1：无限层级分类怎么设计数据库？

**考点**：实际业务中极常见的需求。

**回答**：最常用的是**邻接表**——每个节点存 `parent_id` 指向父节点。优点：简单、修改方便。缺点：查子节点需要递归。MySQL 8.0 支持 CTE 递归（`WITH RECURSIVE`），查询所有子孙节点不再是问题。如果树不深（3-4 层），邻接表足够了。如果树很深且经常查询"某节点的所有子节点"，可以考虑补充`path`字段（如 `1/2/4`）加速查询。

**加分点**：能说出其他方案——嵌套集（Nested Set）查询快但插入慢、闭包表（Closure Table）能快速查任意父子关系但需要维护额外表。能根据场景做选择："树深度 < 5，变更频繁 → 邻接表 + CTE；树深度 > 10，查询为主 → 嵌套集"。

## Q2：MySQL 8.0 的 JSON 列适合替代 EAV 吗？

**考点**：对新技术和旧模式的取舍。

**回答**：大部分场景适合。JSON 列的优势：(1) 一条 JSON 对应一个实体的所有属性（不需要 JOIN），(2) 支持虚拟列 + 虚拟列索引做查询优化，(3) 有类型检查（JSON_VALID）。EAV 仅适用于：需要跨所有属性做全局分析（如"统计所有产品有多少种颜色"）且 MySQL 的 JSON 查询能力不够。但 MySQL 不是做这种分析的最佳工具——这种场景应该交给搜索引擎或列式数据库。

**加分点**：能说出 JSON 列的缺点——更新效率不如 EAV 的独立行、大 JSON 可能超出 InnoDB 行大小限制。能提到虚拟列索引（`GENERATED ALWAYS AS ... STORED` + 索引）的使用场景。
