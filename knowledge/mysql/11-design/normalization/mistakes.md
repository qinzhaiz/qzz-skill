# 常见错误

## 错误 1：过度范式化

**症状**：数据库有几百张表，查询一个简单页面要 JOIN 10+ 张表。页面加载要好几秒。

**原因**：盲目追求高范式（4NF、5NF），导致表拆得太细。每次查询都要大量 JOIN，反而比适度冗余慢得多。

**怎么修**：3NF 就够了。对于高频查询但低频更新的数据，反范式化（冗余字段）是合理的。查询频率和性能需求决定范式的实际边界。

## 错误 2：不知道什么时候该反范式化

**症状**：严格遵循 3NF，但订单列表页面加了缓存还是很慢。

**原因**：JOIN 的代价被低估了。以订单列表为例——每页 20 条订单，每条 JOIN 一次用户表 → 实际上是 21 次查询或一次大 JOIN。每秒 1000 次这样的请求 → 大量 CPU 消耗在 JOIN 上。

**怎么修**：以查询频率和数据修改频率的比值做判断。比值 > 100:1（查询 100 次才改 1 次）→ 考虑反范式化。但要注意反范式化的代价——冗余字段的更新要在业务代码中保证一致性。

## 错误 3：把"慢"归咎于范式化

**症状**：查询慢就觉得是"范式害的"，然后大量加冗余字段。

**原因**：慢的真正原因可能是不合适的索引、不合理的 SQL 写法、或者 Buffer Pool 太小。盲目冗余不仅没解决问题，反而引入了一致性风险。

**怎么修**：先用 EXPLAIN 分析查询为什么慢。如果是缺少索引 → 加索引；如果是 JOIN 太多且索引无法优化 → 考虑反范式化。一步到位反范式化不是首选方案。
