# 面试题

## Q1：InnoDB 怎么检测和处理死锁？

**考点**：不只是"发现死锁就回滚"，要理解机制和代价。

**回答**：InnoDB 通过**等待图**检测死锁——每个事务是一个节点，A 等 B 就画一条 A→B 的边。当图中有环时就是死锁。检测发生在请求锁被阻塞时。发现死锁后，InnoDB 选择回滚**修改行数最少**的事务（最小的代价）。可以通过 `SHOW ENGINE INNODB STATUS` 查看最近一次死锁详情。

**加分点**：能说出死锁检测的 O(N²) 代价——每新来一个等待事务都要和所有已在等待的事务做一次环检测。高并发场景下（如秒杀）死锁检测可能吃掉 50%+ 的 CPU。解决方案包括 `innodb_deadlock_detect = OFF` + 缩短 `innodb_lock_wait_timeout`。

## Q2：生产中如何减少死锁？

**考点**：从原理到实践。

**回答**：
1. **固定访问顺序**：如果一个事务要更新多行，总是按同样的顺序（如 id 升序）更新，避免环的出现
2. **小事务**：拆大事务为小事务，减少锁持有时间
3. **加索引**：让锁从全表扫描的几千行变成索引扫描的几行
4. **降低隔离级别**：RC 没有间隙锁，死锁概率显著降低
5. **应用层重试**：不管怎么优化，死锁无法完全避免，必须有重试逻辑

**加分点**：能举例——比如转账场景，A 转给 B 和 B 转给 A，如果都先锁转出账户再锁转入账户，就不会死锁。能提到用 `performance_schema.data_locks` 在测试环境诊断。

## Q3：死锁和锁等待有什么区别？

**考点**：区分两个容易混淆的概念。

**回答**：锁等待是一个事务等另一个事务释放锁——等待有终点（另一个事务提交或超时）。死锁是两个事务互相等——等待永远没有终点。InnoDB 的处理方式不同：锁等待由超时机制处理（`innodb_lock_wait_timeout`），死锁由死锁检测即时处理（立即回滚一个）。死锁必须先被检测出来，因为它不会自然解除。
