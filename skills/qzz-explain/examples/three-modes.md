# 使用示例

## 速览模式

**用户**：什么是数据库索引？

**qzz-explain**：把数据库想象成一本电话簿。没有索引时，找"张三"得从第一页翻到最后一页。索引就像电话簿前面的姓氏目录——先查目录找到"张"姓从第几页开始，直接翻过去就行。

```sql
-- 这就是建索引的样子
CREATE INDEX idx_name ON users(name);

-- 这条查询会用上索引，不用扫全表
SELECT * FROM users WHERE name = '张三';
```

## 深讲模式

**用户**：我想深入理解 MVCC，它到底怎么做到读写不互锁的？

**qzz-explain**：

### 痛苦：没有 MVCC 的时候

想象一个在线商城。管理员正在统计本月销售额（一个复杂查询，需要扫 100 万条订单），这时候有个用户下单了。怎么办？

- 让查询等写入完成？——查询可能跑 30 秒，用户等不了
- 让写入等查询完成？——管理员看到的报表就不准确了
- 加锁串行化？——整个系统吞吐量崩溃

这就是读写冲突——数据库领域最头疼的问题之一。

### 设计：不打仗，各看各的

MVCC 的核心思路是——**不阻塞**。写操作创建新版本，读操作继续看旧版本。就像你正在读一份报告的旧版本，同事在旁边修改，他改他的新版，你手上还是旧版，互不影响。等他改完了，"切换"到新版就行。

为什么是这个方案？另一个选择是加读写锁——写的时候不许读。但数据库读多写少，锁方案会让大部分查询都在等。MVCC 用空间换时间——多存几个版本的数据，省去等待时间。

### 机制

InnoDB 每行数据隐藏了两个字段：
- `trx_id`：最后修改这行的事务 ID
- `roll_pointer`：指向旧版本的指针（形成版本链）

ReadView 记录"我读数据的时候，哪些事务正在活跃"。查询时顺着版本链往前找，找到第一个在我"开始读"之前就已经提交的版本。

```
版本链示意：
  [v3: trx=103] → [v2: trx=101] → [v1: trx=99]
                                         ↑
                                   ReadView 判断这个版本可见
```

### 边界

MVCC 只在 READ COMMITTED 和 REPEATABLE READ 隔离级别下工作。读未提交直接读最新（不加锁也不看版本），序列化直接加锁（不依赖版本链）。

## 纠错模式

**用户**：我理解的索引就是——给每个字段建一个单独索引，查询的时候 MySQL 会挑最快的一个用。

**qzz-explain**：

你说的对了一半——MySQL 确实会挑索引。但关键在于"给每个字段单独建索引"这个策略有问题。

**误解点**：`WHERE a = 1 AND b = 2` 在有 `idx(a)` 和 `idx(b)` 的情况下，MySQL 只会用一个索引。

**实际**：MySQL 通常一次查询只能用**一个**索引。它用 `idx(a)` 找到所有 a=1 的行，然后逐行检查 b 是否等于 2。如果 a=1 有 10 万行，这个过程很慢。

**修正**：对于多条件查询，应该建**联合索引** `idx(a, b)`——MySQL 可以用一个索引同时过滤 a 和 b。

**验证**：假设表有 100 万行，a=1 的有 10 万行，其中 b=2 的只有 5 行。
- 你的方案：用 `idx(a)` 找到 10 万行 → 逐行过滤 b → 扫 10 万行
- 正确方案：用 `idx(a, b)` 直接定位到 5 行 → 只扫 5 行
