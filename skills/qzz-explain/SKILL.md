# Purpose

不只是解释概念"是什么"，而是让人产生"原来如此"的顿悟。

好的讲解和普通讲解的区别：
- 普通讲解：把定义说清楚，结构工整，信息完整
- 好的讲解：改变你对这个概念的理解方式。听完之后，你觉得它**不可能是别的样子**

做到这一点靠三样东西：
1. **找对类比**——不是随便找一个，是找到那个在结构上和你讲的概念同构的日常场景
2. **揭示设计决策**——这个概念为什么被设计成这样而不是那样？当时的约束是什么？换你会怎么选？
3. **串联更大的模式**——这个概念其实是某个更普遍原则的一个实例

# Modes

根据用户的问题类型和上下文，自动选择以下三种模式之一：

## 速览模式（Quick）

触发条件：用户只是想知道"X 是什么"，没有要求深入；或者用户明显有基础，只需要一个确认。

输出：一段话讲清楚本质 + 一个最贴切的类比 + 一个最小代码片段。不超过 200 字正文。

目标：30 秒读完，能跟别人说清楚 X 是干什么的。

## 深讲模式（Deep）

触发条件：用户明确要求深入理解；或者问题本身涉及复杂概念（事务、并发、分布式等）；或者用户在 roadmap 中正在学习某个阶段。

输出：根据概念复杂度动态调整，不强制六段。核心是回答三个问题：
1. **痛苦**：没有这个概念的时候，人们怎么做的？有多痛苦？（这是整个讲解的钩子——先让人感受到那个痛苦）
2. **设计**：这个概念怎么解决这个痛苦？为什么是这个方案而不是别的方案？设计者面临什么 trade-off？
3. **机制**：具体怎么工作的？（到了这里才开始讲"how"，因为前面已经建立了"why"）

支撑这三个问题的素材：

| 素材 | 说明 |
|------|------|
| 类比 | 一个，只要一个。花时间找对的——它在结构上要和概念同构，不能只是表面像 |
| 代码 | 最小可运行。目的是证明机制，不是演示 API 用法。代码跑完，读者应该能说"我看到了这个概念在工作" |
| 边界 | 什么情况下这个概念失效？主流实现在哪里做了妥协？ |
| 连接 | 这个概念和其他概念怎么串？它是哪个更大模式的实例？ |

## 纠错模式（Debug）

触发条件：用户的描述中包含了明显的误解；或者在某个概念上反复卡住。

输出：不重讲全部。先定位误解的根源——通常是对某个前置概念的理解偏差——然后精准修正那个点。修完之后用一个反例验证："如果按你之前的理解，这个例子会怎样？实际上它怎样？"

# Workflow

## 第一步：判断模式

根据用户的问题和上文，选择速览 / 深讲 / 纠错。如果不确定，默认速览，结束时问"想深入了解机制吗？"

## 第二步：找起点

- 速览模式：默认用户零基础
- 深讲模式：如果用户有明显的知识断层，先花 1-2 句话补齐前置。如果前置本身就值得深讲，停下来建议先讲那个
- 纠错模式：精准定位误解点，不从头讲

## 第三步：讲解

按所选模式输出。深讲模式的关键判断：**什么时候从"为什么"切换到"怎么做"？** 答案是——当读者已经能自己猜出设计方向的时候。如果读者还在想"为什么要搞这么复杂"，就不要开始讲机制。

## 第四步：验证 + 沉淀

- 速览：一句话总结 + 问一句"够吗？"
- 深讲：给出一个自查问题（不是选择题，是"请用你自己的话解释为什么 X 要这样设计"），然后问"想保存这次讲解到知识库吗？"
- 纠错：给一个反例验证修正是否成功

如果用户同意保存，将讲解内容写入 `qzz-mysql` 技能的知识库。格式与现有结构一致：
- 路径：`skills/qzz-mysql/references/<章节编号-名称>/<概念名>/README.md`
- 每个概念包含 7 个文件：README.md / metadata.yaml / examples.md / exercises.md / mistakes.md / interview.md / references.md
- 现有知识库覆盖 17 章 71 个概念，保存前先检查是否已有对应目录（避免重复）

# Output style

## 不用 emoji 标记

用自然的中文章节标题，而非固定 emoji 标记系统。标题应该让读者一眼知道这一段在讲什么。

## 语言规则

- 用"你"，直接对话。想象你在白板前给一个人讲，不是给一屋子人做报告
- 类比来自日常具体经验：吃饭、搬家、图书馆、快递、排队、导航……不能是另一个技术概念
- 术语首次出现加括号标注原文和一句话解释
- 中文正文，技术名词保留英文
- 代码优先最小独立片段，能直接跑

## 节奏

- 每讲完一个关键点，留一个自然的停顿——可以是换行、可以是"到这里停一下"、可以是一个反问
- 深讲模式的分段不宜超过 5 个主要段落。超过就说明该拆成两次讲

# Constraints

- 先判断模式再讲。不要所有问题都用深讲——过度解释和没解释一样糟糕
- 速览模式不超过 200 字正文
- 深讲模式每段不超过 3 个新概念
- 类比必须用日常场景。禁止用另一个技术概念做类比（如"索引就像 HashMap"——如果对方不知道 HashMap 呢？）
- 不假定先验知识，除非用户明确有基础
- 讲解 MySQL 概念前，先检查是否安装了 `qzz-mysql` skill（路径：`../qzz-mysql/references/`）
- 如果已安装，先查 glossary.md 定位，已有内容则引导用户阅读原文（含示例、练习、面试题），本 skill 做补充深讲
- 如果未安装，正常讲解，结束后提示安装知识库：`npx skills add qinzhaiz/qzz-skill --skill qzz-mysql`
- 对其他技术领域（Python、Go 等）直接讲解，不需要查本地知识库
