# 练习

## 基础练习

1. 用自己的话解释：为什么"写完立刻读"在读写分离架构下可能读不到数据？画一个时序图说明。

2. 列举至少三种"写完立刻读"的解决方案，并说明各自的适用场景。

## 进阶练习

1. 用 Docker 搭建 1 主 + 2 从的读写分离架构。用 ProxySQL 做中间件路由。测试在主库写入后立即查询，观察是否出现"读不到"的情况。

2. 设计一个轻量级的"强制读主库"方案：用 Redis 做标记，写操作后 5 秒内同一资源的查询走主库。

## 答案

1. 时序：用户 POST 写入 → 主库执行 COMMIT → 返回 200 → 前端跳转列表页 → 请求落到从库 → 此时 binlog 还没传到从库 → 从库没有新数据 → 页面显示空白。原因是异步复制的延迟。

2. 方案：(a) 关键读操作走主库（如订单详情），(b) Redis 临时标记——写操作后 N 秒内读主库，(c) 前端延迟——写入提交后前端等 500ms 再跳转（不推荐，用户体验差），(d) 半同步复制——主库等至少一个从库确认收到 binlog 再返回（性能有影响）。

3. Docker + ProxySQL：配置 mysql_servers（主库写组 10，从库读组 20），query_rules 设置读写路由。写操作后迅速读取 → 观察是否命中延迟从库。如果中间件检测到从库延迟，自动路由到主库。

4. Redis 标记方案：`SET key "order:123" value "1" EX 5` → 应用层拦截器检查标记 → 有标记走主库 → 标记过期后走从库。
