# 常见错误

## 错误 1：备份时忘记带 `--single-transaction`

**症状**：备份脚本没有用 `--single-transaction`，备份期间用户反馈页面 502（数据库查询超时）。

**原因**：默认情况下 mysqldump 给每张表加读锁（`LOCK TABLES ... READ`），备份期间表不可写。如果备份大表需要 10 分钟，这段时间这张表的所有写入都被阻塞。

**怎么修**：InnoDB 表一定加 `--single-transaction`。利用 MVCC 的一致性快照，不需要锁表。绝大多数生产环境应该用这个参数。

## 错误 2：在从库备份没记录 binlog 位置

**症状**：主库挂了，想用从库的备份恢复并建立新的主从——发现没有 binlog 位置信息，不知道从哪里开始同步。

**原因**：`--master-data=2` 会在备份文件中记录主库的 binlog 文件名和位置（以注释形式）。从库做了备份但没有记录这个信息 → 恢复后无法继续做从库。

**怎么修**：备份脚本加上 `--master-data=2`。这个参数对从库也有效（记录的是从库当前同步到的 relay log 位置对应回主库的 binlog 位置）。

## 错误 3：用 mysqldump 备份大数据库

**症状**：数据库 100GB，每天晚上用 mysqldump 备份。备份要 2 小时，恢复测试发现要 8 小时——RTO（恢复时间目标）完全不达标。

**原因**：mysqldump 是逻辑备份（逐行 SQL），恢复时每条 INSERT 都要走完整的 SQL 解析、优化、执行流程。数据量越大，恢复越慢。

**怎么修**：大数据库（> 10GB）用 XtraBackup 做物理备份。恢复时间是文件拷贝时间，几分钟就能完成。
