# 乐观锁与悲观锁

> 两种解决并发冲突的策略——一个"先锁再改"，一个"先改再查有没有冲突"。

## 为什么需要它

多个人同时改同一条数据时，后提交的可能覆盖先提交的结果。这就是并发写冲突。处理这个问题有两种思路：一种是"我改之前先把数据锁住，别人别动"（悲观锁），一种是"我以为不会冲突，改了再说，改了之后检查是不是只有我改了"（乐观锁）。

## 它是什么

| 策略 | 思路 | MySQL 实现 | 适用场景 |
|------|------|-----------|---------|
| **悲观锁** | 我改的时候别人一定也会改——先锁 | `SELECT ... FOR UPDATE` | 冲突概率高（秒杀、库存） |
| **乐观锁** | 我改的时候别人一般不会改——先改再检查 | 版本号 / 时间戳 / CAS | 冲突概率低（用户资料编辑） |

**类比**：
- 悲观锁：去银行柜台办业务，先拿号排队，轮到你才能操作，别人等着。
- 乐观锁：在线编辑 Google 文档，你先写你的，提交时如果别人也改了文档，系统提示"有冲突，请手动合并"。

## 怎么工作

### 悲观锁（FOR UPDATE）

```sql
BEGIN;
-- 先锁住这行，防止别人改
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
-- 检查余额够不够
-- 扣款
UPDATE account SET balance = balance - 100 WHERE id = 1;
COMMIT;
```sql

执行 `FOR UPDATE` 时，其他事务的任何 `FOR UPDATE` 都会被阻塞——这就是"悲观"：假定一定有人来抢。

### 乐观锁（版本号）

```sql
-- 表结构：id, name, age, version

-- 查询当前版本号
SELECT id, name, age, version FROM user WHERE id = 1;
-- version = 3

-- 更新时带上版本号条件
UPDATE user SET age = 25, version = version + 1
WHERE id = 1 AND version = 3;

-- 检查 affected_rows：
-- = 1 → 更新成功
-- = 0 → 版本号变了，被别人改过了，重试
```sql

核心逻辑：`WHERE version = 旧值` 保证只有"在我读之后、在我写之前"没人改过这行的前提下，更新才能成功。

## 怎么用

**用悲观锁的场景**：
- 库存扣减（高冲突，几乎每次同时买都冲突）
- 账户余额修改（不能容忍失败重试导致的用户体感）

**用乐观锁的场景**：
- 用户编辑个人资料（很少并发改同一个用户）
- 文章编辑（冲突概率极低）
- 配置表更新（读写比极高）

## 注意事项

1. **乐观锁的更新失败必须处理**——`affected_rows = 0` 不是数据库错误，是业务逻辑需要重试。
2. **悲观锁可能导致死锁**——多个事务依次以不同顺序锁定多行。
3. **悲观锁有性能代价**——FOR UPDATE 阻塞其他事务的读（如果用 FOR SHARE 可以读）。高并发下悲观锁可能成为瓶颈。
4. **乐观锁不能用在"先查再改"但没带版本号的场景**——那样就变成了"什么锁"都不是的裸更新。
