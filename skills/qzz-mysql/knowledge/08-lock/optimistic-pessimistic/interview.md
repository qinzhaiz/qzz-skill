# 面试题

## Q1：乐观锁和悲观锁有什么区别？分别怎么实现？

**考点**：概念要清晰，实现要具体。

**回答**：两种并发控制策略。悲观锁假定冲突一定会发生，操作前先加锁。MySQL 中用 `SELECT ... FOR UPDATE` 实现——其他事务被阻塞直到锁释放。乐观锁假定冲突很少发生，先操作再检查有没有冲突。MySQL 中用版本号（或时间戳）实现——更新时检查 `WHERE version = 旧值`，如果 `affected_rows = 0` 说明别人已经改过了。

**加分点**：能说出选择策略的判断标准——冲突概率。举例：库存扣减用悲观锁（高冲突），用户资料编辑用乐观锁（低冲突）。

## Q2：MySQL 的乐观锁怎么实现的？为什么不是数据库原生支持的？

**考点**：乐观锁在 MySQL 中是应用层概念。

**回答**：MySQL 没有原生的"乐观锁"语法。乐观锁是通过 WHERE 条件实现的——UPDATE 时加上 `AND version = @old_version`，利用 UPDATE 语句的原子性保证"比较并更新（CAS）"一步完成。如果版本号变了，WHERE 条件不成立，更新影响 0 行。这和 `CAS` 指令的原理一样：比较旧值 + 设置新值是一个不可分割的操作。

**加分点**：能说出乐观锁和 MVCC 的关系——乐观锁依赖快照读读到旧版本号，再在写时检查。MVCC 提供了一致性读，才让乐观锁能安全运行。

## Q3：高并发场景下，为什么悲观锁可能比乐观锁更好？

**考点**：不是乐观锁一定好，要看场景。

**回答**：乐观锁在冲突概率高时会导致大量重试——每个请求都要"读 → 改 → 发现冲突 → 重读 → 再改 → 可能又冲突"。重试带来的额外读和写反而比悲观锁的锁等待开销更大。悲观锁虽然阻塞了其他请求，但每个请求只需要"等锁 → 加锁 → 操作 → 释放锁"，一次通过，没有重试的浪费。所以在秒杀这样的高冲突场景，悲观锁反而更高效。

**加分点**：能给出量化的判断标准——冲突率 < 10% 用乐观锁，> 50% 用悲观锁。中间地带可以混合使用（如先乐观尝试 2 次，失败降级为悲观）。
