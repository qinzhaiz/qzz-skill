# 面试题

## Q1：InnoDB 的行锁有几种？各自的作用？

**考点**：不只是背名词，要理解每种锁解决的并发问题。

**回答**：三种核心类型：
1. **Record Lock**：锁单行索引记录——防止两个事务同时改同一行。
2. **Gap Lock**：锁索引记录之间的间隙——防止其他事务在这个间隙中插入（解决幻读）。
3. **Next-Key Lock**：Record + Gap 的组合，锁一行加它前面的间隙——这是 RR 级别默认的行锁算法。

还有**插入意向锁**：INSERT 前在间隙上加的特殊锁，多个事务同时插入同一个间隙的不同位置时不会冲突。

**加分点**：能说出 RC 级别没有 Gap Lock 和 Next-Key Lock，只有 Record Lock。能说出唯一索引等值查询时 Next-Key Lock 退化为 Record Lock。能提到 `performance_schema.data_locks` 可以查看实际加的锁。

## Q2：为什么说"InnoDB 没走索引等于锁全表"？

**考点**：理解行锁的加锁机制。

**回答**：InnoDB 的行锁不是锁"数据行"，而是锁"索引项"。当 WHERE 条件没有索引可用时，InnoDB 必须全表扫描。扫描过程中，每读到一行就给这行加锁——即便这行在 WHERE 过滤后被丢弃。最终效果是所有行都被锁，退化成了表锁。用 EXPLAIN 看到 `type=ALL` 就要警惕。

**加分点**：能举例——`SELECT * FROM user WHERE name = 'abc' FOR UPDATE`，name 无索引时锁全表。能提到 MySQL 用 `performance_schema.data_locks` 诊断加锁情况。

## Q3：两阶段锁协议是什么意思？对开发有什么影响？

**考点**：理论到实践。

**回答**：两阶段锁协议指——加锁阶段（执行时加锁）和释放阶段（提交时释放）分开。锁只在事务提交时统一释放，不在语句结束后释放。对开发的直接影响是：要把容易冲突的操作尽量放在事务最后，缩短锁的持有时间。如果事务中先更新热点行，然后做了一堆复杂运算才提交，期间所有访问这行的请求都会被阻塞。

**加分点**：能给出实际场景——比如"先减库存后发消息"应该拆成"先发消息后减库存"，或者拆成两个独立事务。
