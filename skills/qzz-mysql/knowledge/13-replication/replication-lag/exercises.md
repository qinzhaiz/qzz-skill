# 练习

## 基础练习

1. 在你的主从复制环境中，在主库执行一个大事务（更新 10 万行），观察从库的 `Seconds_Behind_Master` 变化。

2. 在从库开启并行复制（`slave_parallel_workers = 4`），再次执行大事务，对比单线程和多线程的延迟差异。

## 进阶练习

1. 调研 MySQL 8.0 的 writeset 并行复制原理：什么情况下两个事务可以并行回放？什么情况下不能？

2. 搭建半同步复制环境，测试主库写入性能（TPS）和异步复制相比的差异。尝试模拟网络延迟增加时的表现。

## 答案

1. 大事务在主库执行了 X 秒 → 从库 `Seconds_Behind_Master` 增长到约 X 秒 → 之后逐渐回落。延迟 = 主库执行时间（因为从库也需要同样的时间回放）。

2. 并行复制的效果取决于事务是否冲突。如果大事务是单条 UPDATE（无法拆分并行），并行复制帮助不大。如果是大量小事务在短时间提交，并行效果明显。

3. writeset 并行复制：MySQL 8.0 分析每个事务的 writeset（写入了哪些行）。如果两个事务的 writeset 没有交集（修改了不同的行），就可以在从库并行回放。如果有交集 → 必须串行（保证一致性）。优点：比 LOGICAL_CLOCK 更精确（后者基于组提交，同组可能仍有冲突）。

4. 半同步复制下，每个事务提交需要等从库确认 → TPS 下降（取决于网络 RTT）。网络延迟增加时 TPS 进一步下降——因为每个事务都要走一次网络往返。生产环境主从通常在同一机房（RTT < 1ms），半同步的性能损失在可接受范围内。
