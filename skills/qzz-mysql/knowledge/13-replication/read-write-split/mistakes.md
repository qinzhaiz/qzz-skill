# 常见错误

## 错误 1：所有查询都设成"强制读主库"

**症状**：上了读写分离，但从库上几乎没有流量。所有读都走了主库。

**原因**：开发时为了方便，设置了 `@Transactional` 时强制走主库，或者担心数据延迟就把所有事务内查询都标成"读主库"。主库还是原来那台机器——读写分离白做了。

**怎么修**：只有真正需要"读刚写入数据"的场景才读主库——比如下单后跳转订单详情、支付结果页。绝大多数列表查询、详情浏览都可以接受几百毫秒的延迟。

## 错误 2：把从库当备份

**症状**：主库误删了一张表，以为从库还有数据——结果从库也同步删除了。

**原因**：主从复制同步的是**操作**，不是**数据状态**。主库执行 DROP TABLE → binlog 记录 DROP → 从库重放 DROP → 从库的表也被删了。

**怎么修**：主从复制不是备份！备份需要独立的定时 dump（mysqldump 或 XtraBackup），与生产数据库物理隔离。从库可以用于做备份（减少主库压力），但不能替代备份。

## 错误 3：从库无限扩展

**症状**：公司里给每个微服务都配了单独的从库，主库后面挂了 20+ 台从库。

**原因**：每台从库都从主库拉 binlog——主库需要维护 20+ 个 binlog dump 连接，网络带宽和 CPU 压力随从库数量线性增长。

**怎么修**：用级联复制——主库只同步到 2-3 台"中间从库"，其他从库从中间从库同步。或者做好容量规划：一个主库通常配 3-5 台从库就够了。
