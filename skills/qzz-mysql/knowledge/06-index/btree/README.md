# B+Tree 原理

> MySQL InnoDB 用 B+Tree 存索引。为什么是 B+Tree 而不是别的？因为它是为磁盘读写而生的。

## 为什么不是二叉树

二叉树在内存里很快——O(logN) 查找。但数据量大到内存装不下、必须放磁盘时，问题就来了：

- 100 万行数据，二叉树深度 ~20
- 一次磁盘 IO 寻道时间 ~10ms
- 一次查询 = 20 次 IO = 200ms——太慢了

**核心矛盾：磁盘 IO 太慢，必须减少树的高度。**

## B+Tree 长什么样

```sql
              [30 | 60]                   ← 内部节点（只存 key）
             /    |    \
       [10|20]  [40|50]  [70|80]          ← 内部节点
       /  |  \  /  |  \  /  |  \
     叶子→叶子↔叶子↔叶子↔    叶子          ← 叶子节点（存数据，双向链表连接）
```sql

### B+Tree 的三个关键设计

**1. N 叉树——高度被压缩到极致。**

InnoDB 以 16KB 的"页"为单位读写磁盘，一个内部节点就是一个页。非叶子节点只存索引 key（不存数据），一个 16KB 页能放约 1170 个 key。

3 层 B+Tree 能存的行数：1170 × 1170 × 16 ≈ **2000 万行**。

一次查询只做 2-3 次 IO。

**2. 只有叶子节点存数据。**

内部节点只负责指路——这进一步提高了每个内部节点能存的 key 数量。

**3. 叶子节点用双向链表连接。**

找完一个叶子节点后直接顺着链表往下走，不需要回到上层。**范围查询的巨大优势。**

## 和 B 树的区别

| | B 树 | B+ 树（InnoDB 用的） |
|---|---|---|
| 数据存在哪 | 所有节点都存 | **只有叶子节点存** |
| 内部节点 | 存 key + 数据 | 只存 key（能放更多 key） |
| 范围查询 | 需要回到上层 | 叶子节点链表直接扫 |
| 查询耗时 | 不稳定（可能在高层命中，也可能到底） | **稳定——每次都到叶子** |

## 为什么用 B+Tree 而不是 Hash

Hash 等值查询 O(1)，快——但**范围查询完全不行**。Hash 表里 `age > 20` 和 `age BETWEEN 20 AND 30` 只能全表扫。

B+Tree 天然支持范围查询——叶子节点的链表就是为这个设计的。

## 注意事项

- **B+Tree 不需要"装得下"。** 16KB 一页正好匹配磁盘的 block size——一次 IO 刚好读完一页。
- **树的高度取决于 key 的大小。** 主键用 INT（4B）比 BIGINT（8B）存更多 key → 树更矮。
