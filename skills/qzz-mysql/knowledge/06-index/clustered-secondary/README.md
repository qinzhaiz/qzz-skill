# 聚簇索引和二级索引

> InnoDB 有两种索引：聚簇索引存整行数据，二级索引只存主键值。

## 聚簇索引（Clustered Index）

**叶子节点存的是整行数据。** 数据本身按主键顺序物理存储。

每张 InnoDB 表有且仅有一个聚簇索引。通常是主键。你没建主键？InnoDB 会按这个优先级找：

1. 有 PRIMARY KEY → 用主键
2. 没主键但有 UNIQUE NOT NULL → 用第一个唯一非空列
3. 都没有 → InnoDB 生成一个隐藏的 6 字节 ROW_ID

**所以：主动设主键——自己做数据的主人。**

## 二级索引（Secondary Index）

你自己建的普通索引都是二级索引。**叶子节点存的是主键值，不是整行数据。**

```sql
二级索引（name）              聚簇索引（主键 id）
[name → id]                  [id → 整行数据]
'张三' → 1                   1 → {id:1, name:'张三', city:'北京', age:22}
'李四' → 2                   2 → {id:2, name:'李四', city:'上海', age:25}
```sql

## 回表

走二级索引查数据需要两步：

```sql
1. 在 name 索引中找到 '张三' → 拿到主键 id=1
2. 拿 id=1 回聚簇索引 → 取出整行数据
```sql

第二步就叫**回表**——二级索引不存整行数据，必须回到聚簇索引拿。

### 回表的代价

每次回表 = 一次 B+Tree 查找 = 1-2 次随机 IO。如果查 100 行要回表 100 次——慢。

**避免回表的方法：覆盖索引。** 下一节讲。

## 二级索引的叶子节点结构

```sql
[二级索引列的值] + [主键值]
```sql

例如 `CREATE INDEX idx_name ON user(name)`，叶子节点存 `(name, id)`。这也是为什么二级索引的叶子节点比聚簇索引的"瘦"——只有两列。

## 注意事项

- **主键尽量用自增 INT。** UUID 做主键的话，聚簇索引插入是随机位置→页分裂→写入性能下降。
- **二级索引自动包含主键。** `WHERE name = '张三'` 用 idx_name 索引时，索引本身已经包含 id，不额外存。
- **没有聚簇索引也能查——MySQL 会给你伪造一个。** 但不推荐——你不会想依赖隐藏列。
